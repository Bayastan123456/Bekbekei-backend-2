# Бекбекей — бэкенд на Node.js

Рабочий MVP сервиса доставки продуктов по предоставленному макету `bekbekei.pdf` (65 страниц). Один API обслуживает клиента, сборщика, курьера и администратора.

**Состояние:** локальная разработка и тестирование. SMS-коды выводятся в серверный лог. QR-оплата и возвраты имитируются. Настоящие SMS, банковские платежи, фискализация, карты и push-уведомления не подключены. Для этого нужны выбранные провайдеры и их учётные данные. Запуск с `NODE_ENV=production` намеренно запрещён до реализации настоящих адаптеров.

## Что реализовано

- Клиентский вход по одноразовому SMS-коду: 4 цифры, 5 минут, 5 попыток, повтор через 60 секунд. Код не возвращается через API.
- Телефон и пароль для сотрудников; opaque access/refresh токены, ротация и отзыв сеансов.
- Профиль, три языка `ru/ky/en`, адреса и проверка зоны доставки.
- Магазины, расписания, каталог, категории, поиск, карточки, пищевая ценность, избранное и история покупок.
- Корзина, серверный расчёт, промокоды, подарок по коду, первая бесплатная доставка.
- Заказы с резервом остатков, снимками цен/адреса, идемпотентностью, историей статусов, отменой и повтором.
- Сборка: атомарное назначение, отметка товара, исключение, согласование замены клиентом.
- Курьер: смены, назначение, получение заказа, прибытие, наличные, вручение, ожидание клиента и возврат на склад.
- Тестовые QR-платежи, подписанные webhook, повторные события, полные и частичные тестовые возвраты.
- Рейтинг, начисления и статистика курьера; поддержка с сообщениями.
- SSE-события; задания с таймерами хранятся в PostgreSQL и переживают перезапуск.
- Закрытая админка: заказы, товары, остатки, сотрудники, акции, контент, платежи, задания и аудит.
- SQL-миграции, OpenAPI/Swagger, Docker Compose и интеграционные тесты.

## Структура проекта

```
bekbekei-backend/
├── src/
│   ├── app.ts            # Middleware, роуты, обработка ошибок, Swagger, админка
│   ├── server.ts         # Запуск HTTP-сервера, подключение к базе, остановка
│   ├── worker.ts          # Фоновые задачи: таймауты оплаты, ожидание клиента, возвраты
│   ├── db.ts              # SQL-интерфейс и транзакции PostgreSQL
│   ├── core.ts            # Общие ошибки, валидация, криптография, конфигурация
│   ├── modules/           # Бизнес-логика по доменам, каждый модуль — роуты + обработчики
│   │   ├── auth.ts            # Вход по SMS-коду, вход сотрудников, сеансы, права
│   │   ├── catalog.ts          # Магазины, каталог, адреса, профиль, избранное
│   │   ├── orders.ts           # Корзина, расчёт, оформление, отмена, резерв остатков
│   │   ├── fulfillment.ts      # Сборка заказа, замены, доставка, смены, заработок курьера
│   │   ├── payments.ts         # Тестовые QR-платежи, webhook, возвраты
│   │   ├── admin.ts            # Управление и аудит для админки
│   │   ├── support.ts          # Обращения и сообщения поддержки
│   │   └── events.ts           # SSE-поток событий с проверкой видимости
│   └── scripts/            # Разовые CLI-команды
│       ├── migrate.ts          # Применение SQL-миграций
│       ├── seed.ts             # Демо-магазин и каталог
│       └── bootstrap.ts        # Создание первого администратора
├── migrations/            # Версионируемая схема базы (SQL)
├── public/                # Статическая админ-панель (HTML/CSS/JS)
├── tests/                 # Интеграционные тесты через HTTP и реальные SQL-транзакции
├── docs/                  # Архитектура, передача проекта, OpenAPI-спецификация
├── scripts/               # Служебные скрипты репозитория (генерация OpenAPI и т.п.)
└── docker-compose.yml, Dockerfile  # Контейнерный запуск API и PostgreSQL
```

Модули не разбиты на слои `routes/service/repository` — для MVP это было бы лишней прослойкой. Если модуль вырастет, его можно разнести на эти слои, сохранив границы ответственности (см. [архитектуру](docs/ARCHITECTURE.md#где-что-лежит)).

## Быстрый запуск

Нужны Node.js **24+**, npm и PostgreSQL **17+**. Все команды выполняются из папки проекта.

```bash
npm ci
cp .env.example .env
```

Отредактируйте `.env`:

1. `DATABASE_URL` — подключение к вашей PostgreSQL.
2. `OTP_SECRET`, `PAYMENT_WEBHOOK_SECRET` — два разных случайных секрета длиной от 32 символов.
3. `ADMIN_PHONE`, `ADMIN_PASSWORD` — ваш телефон и пароль от 12 символов для первого администратора.
4. Оставьте `NODE_ENV=development`, `SMS_PROVIDER=log`, `PAYMENT_PROVIDER=mock`.

Секрет можно сгенерировать командой:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

База, демо-каталог и администратор:

```bash
npm run migrate
npm run seed
npm run bootstrap
npm run dev
```

- Админка: http://localhost:3000/admin/
- Swagger: http://localhost:3000/docs/
- OpenAPI: http://localhost:3000/openapi.json
- API: http://localhost:3000/api/v1
- Проверка процесса: http://localhost:3000/health
- Проверка базы: http://localhost:3000/ready

`bootstrap` создаёт только первого администратора и не перезаписывает существующие аккаунты. Затем сотрудников создавайте через админку. Удалите `ADMIN_PASSWORD` из `.env` после первого создания.

Демо-магазин: `10000000-0000-4000-8000-000000000001`. Демо-лимоны: `30000000-0000-4000-8000-000000000001`. Демо-цена лимонов **13000 тыйын = 130 сом**. Магазин работает 09:00–01:00 по Бишкеку; ночью оформление блокируется. Для круглосуточного тестирования установите в админке `opensAt: "00:00"`, `closesAt: "00:00"`.

## Запуск через Docker

В `.env` дополнительно задайте `POSTGRES_PASSWORD` (свой пароль; для интерполяции URL выбирайте безопасный буквенно-цифровой пароль). `NODE_ENV` оставьте `development`. Dockerfile задаёт production по умолчанию, а Compose берёт режим из `.env`.

```bash
docker compose up -d db
docker compose build api
docker compose run --rm api node dist/scripts/migrate.js
docker compose run --rm api node dist/scripts/seed.js
docker compose run --rm api node dist/scripts/bootstrap.js
docker compose up -d api
```

Порты базы и API привязаны к `127.0.0.1`. PostgreSQL хранится в отдельном томе. Не удаляйте том командой `down -v`, если данные нужны.

## Как получить код входа

```bash
curl -X POST http://localhost:3000/api/v1/auth/otp/request \
  -H 'Content-Type: application/json' \
  -d '{"phone":"+996700123456","consent":true}'
```

В терминале API появится запись `{"type":"development.otp","phone":"...","code":"..."}`. Код также доступен администратору на вкладке «Коды входа» в админке или через `GET /api/v1/admin/otp-codes` (требует Bearer-токен ADMIN; эндпоинт отключён при `NODE_ENV=production`). Возьмите код и отправьте:

```bash
curl -X POST http://localhost:3000/api/v1/auth/otp/verify \
  -H 'Content-Type: application/json' \
  -d '{"phone":"+996700123456","code":"КОД_ИЗ_ЛОГА"}'
```

Ответ содержит `data.accessToken`. Для защищённых запросов:

```http
Authorization: Bearer ACCESS_TOKEN
```

Код хранится в базе как HMAC, access/refresh токены — как SHA-256 хеши, пароли — scrypt с индивидуальной солью. Открытый код доступен только вне production — в логе сервера и через `GET /api/v1/admin/otp-codes` для ADMIN. Токен Figma в проект не добавлен.

## Как оформить заказ с фронтенда

1. `POST /me/addresses` — сохраните адрес с координатами.
2. `PUT /cart/items/{productId}` — передайте `storeId` и `quantity`.
3. `POST /checkout/quote` — передайте `addressId`, `paymentMethod: "CASH"` или `"QR"` и дополнительные поля.
4. `POST /orders` — те же поля плюс `expectedTotal` из расчёта; заголовок `Idempotency-Key` обязателен.
5. Для QR вызовите `POST /orders/{id}/payments`, тоже с `Idempotency-Key`.
6. Для тестовой оплаты администратор нажимает «Тест: оплачено» во вкладке «Платежи» либо вызывает `POST /payments/{id}/mock-confirm`.

Если сумма или наличие изменились, сервер вернёт HTTP 409. Получите новый расчёт и покажите изменения клиенту. Платёжный `qrPayload` вида `bekbekei-test://...` — **не банковский QR-код**.

Пример запроса создания заказа:

```json
{
  "addressId": "UUID вашего адреса",
  "paymentMethod": "CASH",
  "expectedTotal": 13000,
  "courierComment": "Позвоните перед доставкой",
  "cashChangeFrom": 20000
}
```

Ответы используют `{ "data": ... }`; ошибки — `{ "error": { "code", "message", "details", "requestId" } }`. Запросы — camelCase, записи базы в ответах — snake_case. Денежные поля всегда целые числа в тыйынах. Пагинация: `limit` (1–100), `offset`.

## События и таймеры

`GET /api/v1/events` — SSE с Bearer-заголовком. Используйте потоковый `fetch`, а не стандартный `EventSource` без возможности задать Authorization. Переподключение поддерживает `Last-Event-ID` либо `?after=123`. После истечения access-токена обновите сеанс и переподключитесь. При восстановлении связи перечитайте заказ через API: база является источником истины.

Обработчик фоновых задач работает внутри сервера каждые 2 секунды. Задания хранятся в `jobs`; несколько экземпляров используют `FOR UPDATE SKIP LOCKED`. Таймеры не зависят от открытого приложения. После 10 ошибок задача остаётся видимой в админке для ручного повторного запуска.

## Проверка

```bash
npm run check
npm run lint
npm run build
npm test
```

`npm run lint` — ESLint (typescript-eslint) с проверкой типов; `npm run lint:fix` исправляет автоматически исправимое. `npm run format` прогоняет Prettier по всему репозиторию, `npm run format:check` — только проверяет форматирование без записи. Линтер требует TypeScript 6.x (`devDependencies.typescript`): typescript-eslint пока не поддерживает TypeScript 7, поэтому версия для разработки временно понижена; `npm run build`/`npm run check` от этого не зависят и работают на любой современной версии TypeScript.

Обычные тесты используют PGlite — встроенную PostgreSQL в WASM. Для проверки с настоящим PostgreSQL и параллельными подключениями:

```bash
TEST_DATABASE_URL=postgres://USER:PASSWORD@localhost:5432/DATABASE npm test
```

Тесты создают отдельную случайную схему и удаляют только её. Тестовый пользователь базы должен иметь права `CREATE SCHEMA`. Используйте отдельную тестовую базу. Переменная не заменяет `DATABASE_URL` работающего приложения.

## Принятые правила MVP

- Один заказ — один магазин; у курьера максимум одно активное задание.
- Отмена клиентом доступна в `AWAITING_PAYMENT`, `CONFIRMED`, `PICKING`. После сборки — решение поддержки о возврате.
- QR-заказ ждёт оплату 10 минут. Если деньги пришли после отмены, создаётся тестовый возврат.
- При замене клиент подтверждает предложение. Для QR цена замены не выше исходной. Принятая замена считается обработанной сборщиком, который предложил товар.
- Если все позиции исключены, заказ отменяется. Стоимость доставки сохраняется при частичном исключении.
- Бесплатная первая доставка резервируется первым активным заказом; отменённый заказ не расходует её. Возврат также возвращает eligibility.
- Промокод один раз на клиента. Отмена освобождает использование. Подарок применяется по явному коду и наличию товара-условия.
- Начисление курьеру: **80 сом за вручение или фактический возврат в магазин**, один раз на заказ. Это демо-тариф по экрану, а не согласованный бизнес-договор.
- Если клиент не отвечает, после прибытия запускается ожидание 15 минут. Затем требуется фактический возврат в магазин. Полученные наличные автоматически не возвращаются: этот случай пока обрабатывается вне приложения.
- Зона доставки — круг вокруг магазина. ETA 20–25 минут — статическая оценка из макета, не расчёт по пробкам.
- Поиск адреса и получение координат выполняет фронтенд через выбранного геопровайдера. API сохраняет координаты и проверяет зону.
- Изображения задаются HTTPS-ссылками; загрузка файлов и объектное хранилище пока не подключены.
- Контент документов в макете не приведён полностью; администратор должен добавить утверждённые тексты. `ageConfirmed` — только интерфейсное подтверждение, не проверка документов.
