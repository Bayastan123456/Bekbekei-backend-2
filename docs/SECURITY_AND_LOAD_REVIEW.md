# Локальная проверка безопасности и нагрузки

Дата: 26 октября 2026 года.

## Область проверки

Проверены исходники API и административного интерфейса, HTTP-поведение локального приложения и зависимости npm. Запросы отправлялись только на `127.0.0.1` со случайным портом. Для каждого нагрузочного сценария создавалась отдельная PGlite-база в памяти с тестовыми данными. `DATABASE_URL` работающего приложения не использовался; новые сценарии принудительно выбирают встроенную базу.

Это ограниченная локальная проверка, а не независимый аудит развёрнутой системы. Не проверялись внешние серверы, TLS, reverse proxy, Docker, реальные SMS и банковские интеграции. Проверка админки включала анализ способов вывода данных; полноценного браузерного сканирования XSS не было.

## Безопасность

Добавлены 15 сценариев в `tests/security.test.ts`:

- Отсутствующие и поддельные токены; запрет доступа клиента к административным данным.
- Запрет повышения роли через профиль.
- Доступ к чужим заказам, адресам и обращениям, попытки их изменения.
- SQL-инъекции в идентификаторах и телефоне: отклонение валидацией без раскрытия SQL/стека клиенту.
- Повреждённый JSON, превышение размера тела, подпись платёжного webhook.
- Запрет кеширования приватных ответов и ошибок обновления сеанса.
- Попытки прочитать `.env`, `.git` и исходники через статические маршруты.
- CORS, защитные заголовки Helmet, отзыв access/refresh при выходе.
- Отсутствие присваиваний `innerHTML`, `insertAdjacentHTML` и `eval` в административном JS.
- Повреждённый gzip, превышение лимита после распаковки, неподдерживаемая кодировка.
- Лимит попыток входа: 30 отказов в доступе, затем 5 ответов 429.

Также выполняются ранее добавленные проверки изоляции SSE, ротации сеансов, маскирования логов, очистки OTP и отключения медленных потребителей SSE.

### Найдено и исправлено

| Проблема                                                | Изменение                                                                               |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Приватные API-ответы не задавали запрет хранения в кеше | `Cache-Control: no-store` для `/api`; SSE сохраняет `no-cache` и добавляет `no-store`   |
| Повреждённый gzip давал HTTP 500                        | Ошибки zlib при статусе 400 преобразуются в безопасный JSON с HTTP 400                  |
| Неподдерживаемая кодировка могла давать HTTP 500        | Возвращается HTTP 415 без внутренних подробностей                                       |
| В сводке админки оставалась вставка HTML-строки         | Вывод через DOM-элементы и `textContent`; подтверждённая эксплуатация XSS не обнаружена |
| Три известных уязвимых зависимости                      | Совместимые версии зафиксированы в `package-lock.json`, см. ниже                        |

## Нагрузка

Полные метрики: [LOAD_TEST_RESULTS.json](LOAD_TEST_RESULTS.json). Измерены 1740 запросов, дополнительно выполнены подготовительные запросы и 10 циклов SSE-подключений. Каждый ответ читался целиком, для запросов установлен таймаут 15 секунд. Ограничения частоты приложения не отключались; отдельные сценарии используют новые экземпляры приложения с отдельными счётчиками лимитов.

- Каталог: по 200 запросов с параллельностью 1, 10, 25 и 50. Все HTTP 200.
- Профиль с авторизацией: 200 запросов, параллельность 25. Все HTTP 200.
- Создание обращений: 100 запросов, параллельность 20. Все HTTP 201, в базе ровно 100 обращений.
- Смешанный поток: 200 запросов примерно за 10 секунд, 20 запросов/сек; 150 чтений и 50 созданий обращений. Все успешны. Задержка клиентского планировщика исключена из latency.
- 50 одновременных оформлений с одним ключом: один HTTP 201, 49 HTTP 200; один заказ и один резерв.
- 20 покупателей последней единицы: одно оформление и 19 ответов 409; остаток 1, резерв 1.
- 20 сборщиков одного заказа: одно назначение и 19 ответов 409.
- Пакет 350 запросов с одного IP: 300 HTTP 200 и 50 HTTP 429.
- SSE: в каждом из 10 циклов три подключения разрешены, четвёртое отклонено; после отмены соединений можно подключиться снова.

Во всех нагрузочных сценариях отсутствовали транспортные ошибки и HTTP 5xx. Числа скорости относятся только к этой машине, встроенной базе и короткому тесту. Их нельзя использовать как обещание производительности production-сервера.

**PGlite сериализует транзакции.** Эти результаты не подтверждают межсоединительные блокировки, дедлоки и производительность PostgreSQL. Нужны отдельная тестовая PostgreSQL и длительный прогон на инфраструктуре, похожей на рабочую. Длительного теста на утечки памяти здесь не было.

## Общие проверки и замечания

Финальный полный прогон: **65 из 65 тестов**. TypeScript, ESLint и сборка прошли.

В одном предыдущем полном прогоне сценарий поздней QR-оплаты неожиданно получил HTTP 401 на расчёте заказа вместо 200, без ожидаемого JSON ошибки. В следующем полном прогоне сбой не воспроизвёлся. Причина не установлена; это замечание требует проверки на стенде и не считается доказанно устранённым.

## Повторение

```bash
npm run test:security
npm run test:load
npm test
npm run check
npm run lint
npm run build
npm audit
```

`test:load` перезаписывает JSON с метриками последнего успешного прогона. Тесты безопасности входят и в обычный `npm test`. Нагрузочный сценарий запускается отдельно. Обычные интеграционные тесты можно направить на **выделенную тестовую** PostgreSQL через `TEST_DATABASE_URL`; новая локальная проверка безопасности и `test:load` намеренно остаются на PGlite.
