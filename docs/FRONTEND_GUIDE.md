# Бэкенд для фронтендера

Этот документ — не про то, как устроен бэкенд внутри (для этого есть
[ARCHITECTURE.md](ARCHITECTURE.md)). Он про то, как **вызывать API снаружи**: что отправлять, что
придёт в ответ, в каком порядке дёргать ручки и что делать, когда сервер отвечает ошибкой.

Если нужна точная схема конкретного запроса/ответа — открой `http://localhost:3000/docs`
(Swagger UI) или `docs/openapi.json`. В этом документе — сценарии и общие правила, в Swagger —
точные поля каждого эндпоинта.

## Три вещи, которые нужно знать до первого запроса

**1. Форма ответа всегда одна из двух:**

```json
// Успех
{ "data": { "...": "..." } }

// Ошибка
{ "error": { "code": "VALIDATION_ERROR", "message": "Человекочитаемый текст", "details": {}, "requestId": "..." } }
```

Полезные данные всегда внутри `data`. Если `data` — массив (список заказов, товаров) — значит это
список, если объект — конкретная сущность. 204-й ответ (например, после `DELETE`) тела не имеет
вообще.

**2. Регистр полей разный у запроса и у ответа.** Тело запроса ты пишешь в camelCase
(`addressId`, `paymentMethod`). Ответ сервер строит из строк базы данных — там snake_case
(`address_id` не бывает, но `created_at`, `payment_status`, `store_id` — сплошь и рядом). Это не
баг, так и задумано: бэкенд не переименовывает поля туда-обратно. Смотри на конкретную схему в
Swagger, не угадывай по аналогии с другим эндпоинтом.

**3. Деньги — это всегда целое число в тыйынах.** `13000` значит 130 сом. Нигде в API нет чисел с
плавающей точкой для денег — только `сумма_в_тыйынах = сумма_в_сомах * 100`. Дели на 100 и
форматируй уже на фронте.

Ещё по мелочи:

- Все защищённые запросы — с заголовком `Authorization: Bearer <accessToken>`.
- Списки принимают `?limit=30&offset=0` (лимит максимум 100).
- Все пути начинаются с `/api/v1`, кроме `/health`, `/ready`, `/docs`, `/openapi.json`.

## Авторизация

### Клиент — вход по SMS-коду

```
1. POST /api/v1/auth/otp/request   { "phone": "+996700123456", "consent": true }
   → 202 { "data": { "expiresIn": 300, "retryAfter": 60 } }

2. (код НЕ приходит в этом ответе — см. "Как получить код в тестовом режиме" ниже)

3. POST /api/v1/auth/otp/verify    { "phone": "+996700123456", "code": "1234" }
   → 200 { "data": {
       "accessToken": "...", "refreshToken": "...",
       "expiresIn": 900, "tokenType": "Bearer",
       "user": { "id": "uuid", "role": "CUSTOMER" }
     } }
```

Сохрани `accessToken` и `refreshToken` у себя (в памяти + надёжное хранилище на мобильном
клиенте). Дальше на каждый запрос добавляй `Authorization: Bearer <accessToken>`.

**Access-токен живёт всего 15 минут.** Когда он истёк, сервер вернёт `401`. В этот момент:

```
POST /api/v1/auth/refresh   { "refreshToken": "<старый refreshToken>" }
→ 200 { "data": { "accessToken": "...", "refreshToken": "...", "expiresIn": 900, "tokenType": "Bearer" } }
```

Старый `refreshToken` после этого **отзывается** — сохрани новый вместо него, иначе следующий
refresh не сработает. Логика "получили 401 → обновили токен → повторили запрос" должна быть
встроена в твой общий HTTP-клиент, а не писаться в каждом месте отдельно — в админ-панели
(`public/app.js`, функция `api()`) есть готовый рабочий пример именно такой обёртки.

Выход: `POST /api/v1/auth/logout` (просто с Bearer-заголовком, тело не нужно) — отзывает текущую
сессию на сервере.

### Сотрудник (сборщик, курьер, администратор) — телефон и пароль

```
POST /api/v1/auth/staff/login   { "phone": "+996700000001", "password": "..." }
→ та же форма ответа, что у otp/verify, только user.role будет PICKER/COURIER/ADMIN
```

SMS для сотрудников не используется вообще — только пароль, который задаёт администратор при
создании сотрудника.

### Как получить код в тестовом режиме

Настоящие SMS сейчас не отправляются (см. раздел «Что здесь реальное, а что — имитация» в
[ARCHITECTURE.md](ARCHITECTURE.md)).
Код виден одним из двух способов:

- В админке на вкладке **«Коды входа»** (`GET /api/v1/admin/otp-codes`, нужен токен ADMIN) — проще
  всего при разработке фронта: открой `/admin/`, зайди администратором, скопируй код.
- В консоли сервера, где запущен `npm run dev` — строка `{"type":"development.otp","phone":"...","code":"..."}`.

Код пропадает из обоих мест сразу после успешного `otp/verify`.

## Главные сценарии клиента по шагам

### 1. Магазины и зона доставки

```
GET /api/v1/stores                                        → список открытых магазинов
GET /api/v1/delivery/availability?latitude=&longitude=    → { available, stores: [...] }
```

Координаты для `delivery/availability` фронтенд получает сам (геолокация браузера/телефона или
выбор на карте) — бэкенд геопоиском не занимается, только проверяет, попадает ли точка в радиус
магазина.

### 2. Главная страница

```
GET /api/v1/home?storeId=<uuid>&language=ru
→ { store, open, content: [баннеры/истории], products: [...], delivery: { fee, etaMinutes, estimate } }
```

### 3. Каталог и поиск

```
GET /api/v1/products?storeId=<uuid>&categoryId=&search=&filter=all|new&language=ru&limit=30&offset=0
GET /api/v1/products/{id}?storeId=<uuid>   → карточка товара + recommendations
```

У каждого товара в списке есть `availability`: `AVAILABLE` / `LOW_STOCK` / `OUT_OF_STOCK` — готовый
статус для бейджа в UI, пересчитывать остатки на фронте не нужно.

### 4. Корзина

```
PUT    /api/v1/cart/items/{productId}   { "storeId": "<uuid>", "quantity": 2 }   → 204
GET    /api/v1/cart                                                              → { storeId, items, subtotal, currency }
DELETE /api/v1/cart/items/{productId}                                            → 204
DELETE /api/v1/cart                                                              → 204 (очистить всю корзину)
```

Корзина привязана к одному магазину. Если в ней уже лежат товары из магазина A, добавить товар из
магазина B не получится (`409 CART_STORE_MISMATCH`) — сначала нужно очистить корзину.

### 5. Оформление заказа — самая важная часть

Это двухшаговый процесс, и шаг 1 **нельзя пропускать**, даже если кажется, что сумму можно
посчитать на фронте:

```
Шаг 1 — расчёт (можно вызывать сколько угодно раз, ни к чему не обязывает):
POST /api/v1/checkout/quote
{ "addressId": "<uuid>", "paymentMethod": "CASH" | "QR", "promoCode": "...", "ageConfirmed": true }
→ { store, address, items, subtotal, discount, deliveryFee, total, currency, etaMinutes, estimate }

Шаг 2 — создание заказа (резервирует остатки, значит делается один раз за попытку покупки):
POST /api/v1/orders
Headers: Idempotency-Key: <случайная строка 8-128 символов>
{ ...те же поля, что в quote..., "expectedTotal": <total из шага 1> }
→ 201 { data: заказ со статусом, позициями и историей }
```

Почему шаг 1 обязателен: цена может отличаться от той, что фронт держит в памяти (товар
подорожал, промокод истёк, изменилась минимальная сумма заказа). `expectedTotal` в шаге 2 — это
подтверждение «я согласен оформить именно по этой цене». Если сумма успела измениться, сервер
вернёт `409 PRICE_CHANGED` — в этом случае нужно заново вызвать `checkout/quote`, показать
пользователю новую сумму и попросить подтвердить ещё раз. Никогда не отправляй в `expectedTotal`
число, посчитанное на фронте вручную.

**`Idempotency-Key` обязателен для `POST /orders` и `POST /orders/{id}/payments`.** Генерируй
новый ключ (например, `crypto.randomUUID()`) на каждую **новую попытку покупки** пользователя.
Если тот же самый запрос нужно повторить из-за сетевой ошибки (не получили ответ, но не знаем,
дошёл ли запрос) — переиспользуй **тот же** ключ: сервер увидит, что заказ с таким ключом уже
создан, и просто вернёт его же с кодом `200` вместо того, чтобы создать дубликат. А вот отправка
того же ключа с **другими** данными (другой адрес, другая сумма) — это ошибка `409
IDEMPOTENCY_CONFLICT`, так тестируют именно "разные ключи для разных покупок".

### 6. Оплата (только для `paymentMethod: "QR"`)

```
POST /api/v1/orders/{id}/payments   (тоже с Idempotency-Key)
→ 201 { id, qrPayload: "bekbekei-test://payment/...", testMode: true, message: "..." }
```

`qrPayload` в тестовом режиме — не настоящий банковский QR, показывать его как QR-код можно для
вида, но платёж им не пройдёт. Подтверждается он вручную: администратор жмёт «Тест: оплачено» в
админке, либо тестовым вызовом `POST /payments/{id}/mock-confirm`. После этого статус заказа сам
перейдёт в `CONFIRMED` — узнать об этом фронт может через SSE (см. ниже) или поллингом
`GET /payments/{id}`.

### 7. Статус заказа в реальном времени

```
GET /api/v1/events
Headers: Authorization: Bearer <accessToken>
```

Это Server-Sent Events, но подключаться нужно **не через стандартный `EventSource`** — у него
нет способа передать заголовок `Authorization`. Используй потоковый `fetch`:

```js
const response = await fetch('/api/v1/events', { headers: { Authorization: `Bearer ${accessToken}` } });
const reader = response.body.getReader();
// читать chunks, парсить строки вида "id: 42\nevent: order.status\ndata: {...}\n\n"
```

При переподключении передай `Last-Event-ID` (заголовок) или `?after=<id>` (query) — сервер
пришлёт только то, что пропустил. **SSE не гарантирует доставку**: если соединение оборвалось и
переподключилось, всегда перечитывай актуальное состояние заказа через `GET /orders/{id}`, а не
полагайся только на поток событий.

### 8. Профиль, адреса, избранное

```
GET/PATCH /api/v1/me
GET/POST  /api/v1/me/addresses
PUT/DELETE /api/v1/me/addresses/{id}
GET/PUT/DELETE /api/v1/me/favorites/{id}
GET /api/v1/me/purchased
```

Ничего неожиданного — обычный CRUD над своим профилем.

### 9. Поддержка

```
POST /api/v1/support/threads               { orderId?, message }   → создать обращение
GET  /api/v1/support/threads                                       → список своих обращений
GET  /api/v1/support/threads/{id}/messages                         → переписка
POST /api/v1/support/threads/{id}/messages  { message }            → написать ещё
```

## Обработка ошибок — что показывать пользователю

| HTTP        | Типичная причина                                                       | Что делать на фронте                                                                       |
| ----------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `401`       | Access-токен истёк или невалиден                                       | Попробовать `auth/refresh`; если тоже не вышло — разлогинить                               |
| `403`       | Не хватает прав (например, сотрудник пытается зайти не в свой магазин) | Показать «недоступно», не повторять запрос                                                 |
| `404`       | Запись не найдена **или нет доступа к ней**                            | Эти два случая специально неразличимы в ответе — не палим чужие ID                         |
| `409`       | Конфликт состояния: цена изменилась, магазин занят, остаток закончился | Обновить данные (например, снова вызвать `checkout/quote`) и показать актуальное состояние |
| `422`       | Не прошла валидация тела запроса                                       | Показать ошибки по полям — они есть в `error.details`                                      |
| `429`       | Слишком много запросов (OTP, вход)                                     | Показать таймер до повтора, не долбить запросами в цикле                                   |
| `500`/`503` | Ошибка сервера / интеграция отключена                                  | Показать общий экран ошибки, не притворяться, что всё ок                                   |

Частые значения `error.code`, которые стоит узнавать по имени и обрабатывать адресно:
`VALIDATION_ERROR`, `UNAUTHENTICATED`, `INVALID_OTP`, `OTP_COOLDOWN`, `INSUFFICIENT_STOCK`,
`PRICE_CHANGED`, `OUTSIDE_DELIVERY_ZONE`, `STORE_CLOSED`, `MINIMUM_ORDER`,
`AGE_CONFIRMATION_REQUIRED`, `INVALID_PROMO`, `IDEMPOTENCY_CONFLICT`, `CART_STORE_MISMATCH`.
Полный список — в Swagger у каждого эндпоинта (ответы 400–503 с описанием).

## Если ты пишешь интерфейс не для клиента

У сборщика, курьера и администратора — те же правила авторизации и формата ответов, но свои
наборы эндпоинтов: `/picking/*`, `/delivery/*` и `/courier/*` для сборщика/курьера,
`/admin/*` для администратора. Рабочий пример фронтенда для админки уже есть в `public/` — весь он
на чистом JS без сборки, и видно, как устроены запросы, обновление токена и формы (см. `app.js`).

## Шпаргалка для тестового режима

- Магазин по умолчанию: `10000000-0000-4000-8000-000000000001`.
- Код входа клиента — в админке («Коды входа») или в логе сервера, см. выше.
- QR-оплата нигде по-настоящему не проходит, подтверждается вручную через админку.
- Магазин по умолчанию работает 09:00–01:00 по Бишкеку; ночью оформление будет падать с
  `STORE_CLOSED` — это не баг.
- Промокод `WELCOME10` — 10% скидка, уже создан в демо-данных.

Полный актуальный список демо-данных и shell-примеры с `curl` — в [README](../README.md#быстрый-запуск).
