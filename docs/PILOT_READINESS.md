## Реализованный контракт

### Поддержка (B06)

- `GET /api/v1/support/threads/{id}`: владелец и ADMIN читают также закрытые обращения; чужому — 404. Поля: id, user_id, order_id, status, created_at, updated_at. updated_at — создание/последняя смена статуса; для старых строк исходное значение равно created_at, историческую дату закрытия восстановить нельзя.
- `GET /api/v1/support/threads/{id}/messages?latest=true&limit=30` открывает последние сообщения. Все страницы возвращаются по возрастанию `(created_at,id)`.
- `before={message UUID}` — предыдущая страница; `after={message UUID}` — следующие сообщения. Курсор обязан принадлежать этому обращению. Одновременно before и after запрещены. Курсор/latest несовместимы с offset. Без этих параметров старые limit/offset работают как прежде.
- Метаданные: `meta: {hasMore,before,after}`; before/after — крайние ID страницы, null для пустой. hasMore относится к направлению выбранного запроса, а не сразу к обоим направлениям. При after нужно продолжать чтение, пока hasMore=true.
- `POST /api/v1/support/threads/{id}/messages`: `{ "message": "Текст", "clientMessageId": "UUID" }`. UUID генерируется один раз и сохраняется клиентом до получения ответа. Область уникальности: обращение + автор. Повтор возвращает исходное сообщение с тем же id и HTTP 201, включая повтор после закрытия. Другой текст после trim — 409 IDEMPOTENCY_CONFLICT. Новая отправка в закрытый диалог — 409 THREAD_CLOSED. Старый клиент может не передавать ключ, тогда гарантии повтора нет.
- Проверка статуса, запись и события выполняются под блокировкой строки обращения в одной транзакции. Повтор отправки не публикует повторное событие. Статусные PATCH также блокируют строку; повтор статуса не создаёт событие.
- SSE `support.status`: `{ "threadId": "UUID", "status": "OPEN|CLOSED" }` владельцу при создании/смене статуса; ADMIN получает смены статуса. Старые `support.opened` для ADMIN и `support.message` сохранены. При потере SSE клиент перечитывает целевой GET.

Пример ответа страницы:

```json
{
  "data": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "author_id": "22222222-2222-4222-8222-222222222222",
      "body": "Здравствуйте",
      "created_at": "2026-11-06T10:00:00Z",
      "client_message_id": null
    }
  ],
  "meta": {
    "hasMore": false,
    "before": "11111111-1111-4111-8111-111111111111",
    "after": "11111111-1111-4111-8111-111111111111"
  }
}
```

Пример ошибки (middleware может добавить requestId):

```json
{ "error": { "code": "IDEMPOTENCY_CONFLICT", "message": "Ключ использован для другого сообщения" } }
```

### Начисление конкретной доставки (часть B09)

`GET /api/v1/courier/deliveries/{id}/earning` доступен только текущему назначенному курьеру. Возвращает order_id, status, amount, created_at, currency=KGS. POSTED означает записанное начисление (включая 0); PENDING — активная доставка без начисления; UNKNOWN — завершённая/отменённая доставка без начисления. amount=null не заменяется нулём и не означает доход в размере заказа. Для отмены UNKNOWN не обещает будущую выплату. Проверки полного наличного цикла включают переход PENDING → POSTED и отказ чужому курьеру. История дополнена сортировкой по id при одинаковом updated_at; offset по-прежнему не даёт снимка при изменяющемся наборе.

### Контакты и магазин (B03, частично)

Детали заказа содержат `recipient: {first_name,last_name,phone}` и `pickup: {id,name,address,latitude,longitude}`. Источник recipient — текущий профиль покупателя; источник pickup — текущая запись магазина. Это не исторические снимки. Отдельный получатель, отличающийся от покупателя, пока не моделируется.

Детали доступны владельцу, назначенным сборщику/курьеру и ADMIN через существующий accessOrder. Очередь неназначенных доставок контакт не раскрывает. Изменение назначения немедленно лишает прежнего исполнителя доступа к деталям и командам. Самой административной команды переназначения это изменение не добавляет.

## Миграция и восстановление

`004_support_delivery.sql` добавляет updated_at обращения, nullable client_message_id и индексы уникальности/курсора. Старые сообщения имеют client_message_id=null; сообщения не удаляются. Сначала резервная копия и `npm run migrate`, затем новый сервер. Миграции запускаются транзакционно под общей блокировкой schema_migrations; повтор безопасен, применённые файлы не редактировать.

При откате приложения оставить добавленные столбцы и индексы: старый сервер их игнорирует. Старый сервер при этом перестаёт обеспечивать новые гарантии идемпотентности и статусные события. Для отката данных использовать проверенную резервную копию отдельного тестового окружения; down-миграции с потерей сообщений не предусмотрены.

## Flutter

После обновления тестового сервера можно заменить поиск обращения в списке на GET /threads/{id}, offset-пробы последних сообщений на latest/before/after и подключить support.status. При reconnect/возврате на экран продолжать целевое чтение для восстановления после пропуска события. Сохранять clientMessageId вместе с неотправленным сообщением и повторять тот же ключ. Подключить recipient/pickup в деталях назначенной доставки. Старые offset, тела без clientMessageId и события остаются совместимыми.

## Проверки

Новые интеграционные сценарии проверяют 111 сообщений, одинаковые timestamps, отсутствие пересечения страниц, after, неверный курсор, доступ чужого пользователя, одновременный повтор отправки, конфликт тела, повтор после закрытия и события OPEN/CLOSED/OPEN. Проверка контактов включает неназначенную очередь и отзыв доступа после изменения назначения в БД; она не подтверждает наличие административной команды передачи.

Локальная PGlite сериализует транзакции; это не доказательство корректности конкуренции PostgreSQL. Для отдельного тестового PostgreSQL запустить `TEST_DATABASE_URL=... npm test`: каждый testDatabase создаёт отдельную схему и удаляет её при завершении. Не использовать production-учётные данные. Реальные SMS, банк/возврат, push, физические устройства и сквозной Flutter-прогон здесь не проверены.

Последний полный локальный прогон: **67/67 тестов успешно**, Node + PGlite; `npm run check`, `npm run lint`, `npm run build` успешно. До итогового прогона один платёжный тест разово вернул 404; отдельно и в итоговом полном прогоне прошёл. Причина разового сбоя не установлена. Это ограничение воспроизводимости следует учитывать при PostgreSQL-приёмке.
